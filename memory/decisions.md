# 設計決策紀錄

這裡記錄「未來還會用到」的決定與理由，不是聊天記錄。判斷標準：下一個接手的人會不會問「為什麼這樣做」。

格式：

```
## YYYY-MM-DD 決定的一句話標題
- 情境：當時面對什麼
- 決定：做了什麼
- 理由：為什麼這樣而不是那樣
- 影響：之後誰會被這個決定綁住
```

---

## 2026-08-30 內容與版型分離，網站從 content/ 長出來

- 情境：需要一個 AI 能長期維護的客服知識頁，而不是一次性產出的 HTML。
- 決定：`content/*.md` 是唯一內容來源，`design/` 是版型契約，`site/` 全部由建置產生，不得手動編輯。
- 理由：內容一旦寫死在 HTML 裡，每次更新都要 AI 重新理解整份版面，錯誤率高且無法驗證。分離之後，改內容不會動到版型，改版型不會動到內容。
- 影響：任何人要改站上文字，都必須回到 `content/`，不能直接編輯 `site/`。

## 2026-08-30 版型契約凍結，並以編號規則對應驗證器

- 情境：版型規範若只是文件，AI 每次產出都可能漂移一點，累積下來就走樣。
- 決定：`design/brief.md` 每條規則標記 `[GATE]` 或 `[REVIEW]`，`[GATE]` 由 `scripts/validate.py` 實際擋下，錯誤訊息回報規則編號。
- 理由：靠人眼審查版型不可靠也不可規模化。能被機器檢查的規則就該被機器擋，剩下的才交給人。
- 影響：新增版型規則時，必須同時決定它屬於哪一級；標成 `[GATE]` 卻沒有對應檢查，等於謊稱有把關。

## 2026-08-30 色彩全部走 token，樣式表本體禁止色碼字面值

- 情境：深色模式與品牌色調整時，散落各處的色碼會漏改。
- 決定：`design/tokens.json` 是色彩唯一真實來源，建置時注入 `:root`；驗證器會掃描 `site/assets/style.css`，token 區塊以外出現 `#RRGGBB` 或 `rgb()` 一律擋下。
- 理由：這是 L2 驗收句「把 brief 藏起來樣式會不會跑掉」的具體實作。色碼寫死在別處，就是樣式脫離契約的證據。
- 影響：新增元件時不能順手寫一個顏色，必須先在 tokens.json 定義。

## 2026-08-30 缺資料時留白並回報，不使用佔位符

- 情境：客服知識頁的金額、天數、期限若寫錯，比沒寫更糟。
- 決定：驗證器擋下 `TODO`、`待補`、`XXX`、`（略）` 等標記。來源沒講清楚的資訊，整段不寫，改列進待確認清單交給人補。
- 理由：佔位符會隨著一次疏忽直接上線，而空白至少不會誤導使用者。
- 影響：AI 不能用「先寫個大概之後再補」的方式交付，缺資料一定會浮上檯面。

## 2026-08-30 列印展開改用 beforeprint 腳本，不用純 CSS

- 情境：版型契約要求列印時所有問答展開。
- 決定：以 `beforeprint` 與 `afterprint` 事件強制展開 `details`，而非在列印樣式中設 `display: block`。
- 理由：收合狀態的 `details` 內容不會被瀏覽器渲染，不是單純的 `display: none`，純 CSS 無法攤開。原本寫的 CSS 規則是無效的，已移除。
- 影響：列印展開屬於漸進增強，關閉 JavaScript 時列印仍會是收合狀態，這是已知且接受的限制。

## 2026-08-30 restricted/ 由 settings.json 硬擋，並承認其覆蓋範圍有限

- 情境：L4 要求敏感資料 AI 讀不到，且必須是系統擋而不是模型自律。
- 決定：`.claude/settings.json` 的 `permissions.deny` 封鎖 `restricted/` 的讀寫，以及 `cat`、`head`、`tail`、`grep` 等常見讀取指令；`source/` 唯讀；`inbox/` 在 Day 1 一併封鎖。
- 理由：寫在 CLAUDE.md 的是軟規則，模型可能違反；寫在 settings.json 的由系統攔截，模型無從繞過。
- 影響：**這層防護不是密不透風的。** deny 清單是逐條比對，繞道的讀取方式（例如透過 `python3 -c` 開檔、或未列舉的指令）不會被這幾條擋下。真正的敏感資料不應該放在 AI 有檔案系統存取權的機器上，這裡的設定是課堂邊界演示，不是資安方案。

## 2026-08-30 內容清回 L0 空殼，等待 source/ 到位

- 情境：先前已把四個內容檔填成一個虛構品牌的客服內容。之後收到的專案規格顯示，內容必須由 `source/` 蒸餾而來，且 L0 階段本來就規定「一個字都不填」。
- 決定：把 `content/` 四個檔清回 0 bytes 空檔，保留引擎、版型契約、驗證器與骨架。
- 理由：那批文字是憑空生成的，留著會被誤認為正式內容，也違反「沒有一個字是憑空生的」。而且 `source/`、`restricted/`、`inbox/` 目前不在 repo 裡，沒有來源就無法執行蒸餾，硬做等於再憑空生一次。
- 影響：`scripts/validate.py` 在這個狀態回傳離開碼 2 並明確標示「L0 空殼」，不是 0 也不是 1。內容進來之前，網站無法建置，這是預期行為。

## 2026-08-30 驗證器新增離開碼 2，區分「尚未開始」與「違規」

- 情境：內容清空後，驗證器一次噴出 15 條衍生錯誤，真正的訊號被淹沒。
- 決定：偵測到所有內容檔皆為空時，印出空殼說明並回傳離開碼 2，不再逐條列出衍生錯誤。
- 理由：把「還沒填」誤報成「違規」會讓人以為架構壞了。但也不能回傳 0，那等於謊稱可以交付。
- 影響：CI 或腳本串接時要分辨三種碼：0 通過、1 違規、2 尚未填寫。

## 2026-08-30 自我測試改用 fixture，不依賴真實內容

- 情境：`selftest.py` 原本讀 `content/` 的現況做斷言，內容一清空測試就全垮。
- 決定：改用臨時目錄建立最小內容集，測試完全不碰 `content/`。
- 理由：驗證器的測試應該測驗證器，不是測當下的內容。兩者綁在一起，會在內容變動時產生假警報，久了就沒人理它。
- 影響：新增驗證規則時，要同時在 fixture 補對應案例，維持「會擋違規」與「不誤殺合法內容」兩面都測。

## 2026-08-30 build-page 保留兩條路線，腳本為預設

- 情境：專案規格寫「純 HTML、不用框架」，但沒有指定產生方式。腳本產生與 AI 直接寫 HTML 各有取捨。
- 決定：`SKILL.md` 預設走腳本路線，並明文記載「直接撰寫 HTML」的退場機制與適用條件。
- 理由：腳本產生確定一致且可驗證，適合日常維護；但引擎故障、缺少 Python、或需要示範「只靠契約也能做出一致頁面」時，必須有路可走。把退場機制寫進契約，比臨時即興決定安全。
- 影響：走路線 B 的產出是暫時的，引擎恢復後要回到路線 A 重新產生，且必須在本檔記錄原因。

## 2026-08-30 品牌色標記為待確認的工作值

- 情境：版型契約需要指定品牌色，但目前沒有拿到正式品牌規範。
- 決定：`design/tokens.json` 先採一組中性藍為主色，並在 `design/brief.md` 0.3 節明確標記「這是待確認的工作值，不是已核定的品牌色」。
- 理由：不標記就會被下一個人當成已核定。標記出來，替換時只需要改 tokens.json 一個檔。
- 影響：拿到正式品牌規範後，不需要動任何一行樣式表或樣板。這一點同時是版型契約是否真的在發揮作用的檢驗方式。

## 2026-08-30 示範首頁走路線 B，直接撰寫 HTML

- 情境：需要一個可看的客服首頁，但 `content/` 是空的，且今日暫行規則禁止填寫 `content/`。
- 決定：依 `SKILL.md` 的退場機制走路線 B，直接寫 `site/index.html`，內容全部使用明確標示的佔位資料，頁面頂端加上 `.demo-notice` 聲明這是版型示範。
- 理由：路線 A 需要先填 `content/`，那會違反暫行規則，也會在沒有 `source/` 的情況下憑空生成客服內容。路線 B 只示範版型，不宣稱任何服務條件。
- 影響：**這份產出是暫時的。** `content/` 一旦填入真實內容並跑 `build.py`，這個檔案會被覆蓋，這是預期行為。樣式與 class 全部沿用既有樣板，沒有新增行內樣式。

## 2026-08-30 修正搜尋載入的競態，快取請求而非布林旗標

- 情境：實際渲染測試時，搜尋「保固」回傳零筆，但索引裡確實有相符項目。
- 決定：`load()` 改為快取進行中的 `fetch` promise，取代原本的 `loading` 布林旗標。
- 理由：舊寫法在 `focus` 觸發的載入尚未完成時，接著的 `input` 事件會拿到一個立即完成的 promise，於是在 `entries` 仍為 null 時就渲染，結果永遠是零筆。真實使用者只要點進搜尋框後馬上打字就會踩到。
- 影響：這個 bug 靠讀程式碼不容易發現，是實際用瀏覽器跑才抓到的。日後改動搜尋載入邏輯時，要保留「同一份請求只發一次、後續呼叫等同一個 promise」這個性質。
